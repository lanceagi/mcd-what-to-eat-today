# 今天吃什么 · v2

一个点单对话 Skill:把门店柜台那套流程搬进对话,一次问一件事,用户回一个数字。

MCP 负责执行,本 Skill 负责**问什么、怎么问、说什么**。

## 〇、核心意图（产品宪法）

2026-10-11 00:02 李现校准。三条按原意记录，任何改动不得与它们冲突：

> **1. 获取用户的喜好，在不同场景为用户提供套餐推荐。**
> **2. 这个 Skill 的设计本意是语音的交互下单。**
> **3. 把门店的完整下单体验还原。精髓在于：通过这个 Skill，
>    这位 AI 服务员十分了解你的喜好，让你有宾至如归的感觉。**

### 三条意图对应的实现状态（2026-10-11 阶段 A 完成,如实记录）

| 意图 | 已做到 | 还差什么 |
|---|---|---|
| 1 喜好 → 场景化套餐推荐 | 画像四层:签名(去芝士/少冰)+ **habits 时段习惯** + **taste 口味偏好** + **avoid 拒单记录**;场景实现 **5 个**(健身/省钱/赶时间/随缘/尝新六维) | 团餐助餐选择;try_new 热量差对套餐口径依赖营养表,数据不全时如实标注 |
| 2 语音交互下单 | 🔤 **架构已合并(阶段 A B 组)**:`Turn.text` + `Turn.speech` 同源产出;voice.py 只留口播工具(中文数字/术语归一/复述确认),不再自带状态机;ASR 口语进 `_reply` 前先归一(打包→外带);`--flow-demo` 走完 S0→S8 | TTS/ASR 本体在宿主 App,MCP 零语音接口(边界不变) |
| 3 全套门店体验 + 宾至如归 | S0–S9 全链;迎宾门禁(A4):有历史订单时必须命中「常点什么/什么时候来/上次要什么」至少一维,通用客套会被拦(selftest 反例验证);S0 口播吃 habits/taste 层 | 「什么时候来」维度目前主要在夜宵/早餐分支触发,午晚餐常规时段命中常点/上次两维 |

### 由此确定的两条设计原则

1. **语音是主入口，文字是降级形态。**
   `flow.Flow` 的每个 `Turn` 必须同时产出 `text`（一屏可读）与 `speech`（≤6 秒可念）。
   两套状态机必须合并成一套。
2. **每一轮都要能证明「我了解你」。**
   门店店员让客人觉得熟悉，靠的是记得住三件事：**你常点什么、你什么时候来、你上次要什么**。
   Skill 的每一轮至少命中其中一件，否则这一轮就是通用客服话术。

### 五条硬规则

1. **渠道必须问。** 历史众数只给选项加 ★,不给免问权。渠道猜错要退单重做,代价不对称。
2. **一次只问一件。** 被否定立刻换方向,不连续追问。
3. **间隔天数只陈述,不预测。** 实测点单间隔 1~16 天,方差过大,禁止「你该吃了」。
4. **编号只在上一条消息内有效。** 下一轮立即作废,防止「上轮的 1 被当成本轮的 1」。
5. **地址必须先确认。** 未确认收货地址前不拉、不报门店列表(2026-10-11 用户反馈:「你都没和我确认地址,怎么预判我周围有什么店」);门店全打烊时如实报每家开门时间,禁止「?」占位和「营业时间未知」静默降级。

## 六、实测铁律(11 条)

### 1. `reservationDate` 必须落在营业时间内，且要在可预约深度内

门店对象带 `businessStatus` / `businessStartTime` / `businessEndTime`,**必须读**。
用「当前时间+2h」这种算法晚上必挂,报 `600057 门店可能已关闭或不在营业时间`。
`channel.pick_when()` 分四档兜底:营业中 +5min / 未到营业取开门 / 已过营业改约次日 / 已打烊直接报。

🔴 **「在营业时段内」不等于「可预约」**(test/test-3 缺陷 D2,2026-10-10 23:19 实测):
23:19 时算出 `reservationDate=23:24`,仍在营业时段内,但 `create-order` 报
`600054 预约时间不在可预约时间范围`。改用**即时单(不传该字段)**成功建单。

→ 距打烊不足 `IMMEDIATE_MARGIN`(30 分钟)时,`channel.is_immediate()` 返回 True,
`create-order` **不许传 `reservationDate`**。`query-meals` 仍需要未来时间,照常传。

⚠️ 另一条实测:**早餐时段的菜单不同**。次晨 07:10–10:10 查某单品报 `60006`,
那不是售罄,是该时段菜单里没有这个编码。

### 2. `query-nearby-stores` 必须显式传 `searchType=2` + city + keyword

默认值是 1(搜索**收藏**餐厅),用户没收藏记录时报 `600050 收藏餐厅列表为空`。
⚠️ 该接口返回的 `longitude`/`latitude` **恒为 0.0**,它是关键词搜索。
**禁止对用户说「附近的门店」**,只能说「你搜的关键词命中的门店」。

### 3. 商品编码跨渠道、跨门店都不通用

| 商品 | 外送 | 到店 |
|---|---|---|
| 培根安格斯厚牛堡 | `902060` | `511781` |
| 可口可乐 | `903050`(可口可乐中杯) | `9900008751`(可乐) |
| 雪碧 | `903060` | `3010` |

同一门店两渠道菜单重叠仅 26/122;同城同日菜单项数从 67 到 125 不等。
(README 记 25/117,为另一日两次实测 —— 菜单每日在变,重叠比本身不稳定,量级才是结论。)
**菜单必须逐店逐渠道拉,且商品名都不同。**

`60006 商品已售罄或不可售` 是**误导性信息**,真因是编码不属于该渠道。用 `channel.explain_error()` 转译后再向用户解释。

### 4. `beCode` 不能凭空填,且与 `beType` 成对

外送/得来速/团餐缺 beCode 报 `600048`。唯一来源是 `delivery-query-stores` 或 `query-nearby-stores`。
**同一 storeCode 在不同 beType 下 beCode 不同**:145027902(beType=2)/ 145027981(beType=6)。切渠道不能只换 storeCode。

### 5. 定制有两类结构,组装规则完全不同

| 类型 | 判据 | 规则 |
|---|---|---|
| A 型 可移除配料(汉堡) | 组内任一项有 `unselectedKey` | **组内所有项都必须传**,选中传 `selectedKey`,未选中传 `unselectedKey`。漏传任何一项下单失败 |
| B 型 单选(饮料冰量) | `unselectedKey` 全为 None | 4 项共用同一 code,靠 key 区分,**只传选中的那一项** |

签名挂不上时要**如实报「未挂上」**,不许静默。实测:`9900008751 可乐` 名称命中「可乐」但 `modification` 是空组,按名字顺序取会取到挂不上签名的那个。

### 6. 营养数字必须带口径(单品 / 整份)

🔴 2026-10-10 23:26 外部 agent 实测抓出:健身场景报「麦香鱼 325kcal / 钠 556mg」,
用户以为是整份套餐,实际整份是 **761kcal / 钠 721mg**,当场追问「怎么比之前报的高这么多」。

根因:`rank_fitness` 只查 `nut_of(nutrition, m["name"])`,而营养表里**没有套餐**
→ 所有套餐被 `if not n: continue` 排除 → 只剩裸堡和小食。

修法三条,缺一不可:

| # | 规则 |
|---|---|
| 1 | 套餐走 `combo_nutrition()` 叠子项;任一轮查不到则整体标「数据不全」,不许少算 |
| 2 | 单品循环必须**排除套餐名** —— `nut_of` 会把「麦香鱼套餐」模糊匹配到「麦香鱼」的 325kcal |
| 3 | 每行渲染都要写 `scope`(单品/整份)。**不带口径的数字等于没说** |

排序也修了:原排序只看蛋白/价格,前几名全是小食(吉士汉堡包 ¥16.5 / 汉堡包 ¥15)。
健身场景要的是**一份主食**,现在主食/套餐优先。

### 7. 场景推荐必须吃当轮渠道

🔴 同一次实测:用户选了**外带**,`recommend.py` 却按历史众数(麦乐送)拉菜单报价,
用户追问「你这个价格是外送的价格吗」才发现差 ¥5.5–6。

**对话内一律走 `flow.Flow.ask_scene()`**,它用 `self._params()` 取当轮渠道。
命令行必须显式带 `--channel-hint`。

同店 1450523 跨渠道实测价差(2026-10-10 23:0x):

| 套餐 | 外带(到店自取) | 麦乐送 |
|---|--:|--:|
| 麦香鱼中套 `9900005460` | ¥33.5 | ¥39.5 |
| 双层深海鳕鱼堡中套/三件套 | ¥36 | ¥41.5 |

### 8. 已取消订单不进画像

`order-list.data.list[].orderStatus` 取值见过「订单已完成」「订单已取消」。
**已取消的单必须剔除** —— 用户没付款的单不能算进「照旧」和签名统计。

2026-10-10 21:33 那笔取消单曾被算成「少冰第 2 次」,导致间隔说成「昨天刚吃过」,
而它从没成交。剔除后可见订单 9 单、跨度 51 天。

剔除记录写进 `profile.json` 的 `droppedOrders`(只留单号后 8 位 + 状态 + 时间)。

### 9. 套餐的读结构与写结构完全不同

```
query-meal-detail 返回  rounds:[{id, choices:[{code, quantity, modification}]}]
create-order 要的是    roundList:[{round:"<字符串>", comboItemList:[{code, quantity, modification}]}]
```

⚠️ `round` 是**字符串**。照着 `rounds` 写 → `500 服务器发生了未知的问题`。
用 `order_builder.build_combo_item()`。

### 10. 「约开门后送」必须落在可预约窗口,不是营业开始时间

门店 06:30 开门 ≠ 06:30 可约:沪太路341号营业 06:30 起,早餐可约窗口 07:00 起,
直接约 06:30 会撞 `600054`。`channel.next_slot()` 解析今日 `reservationTimeOptions`
取下一个可约时刻,解析不出才回退 `pick_when()`。

🔴 2026-10-11 凌晨实测事故:测试地址附近的三家配送店全打烊,
`pick_store` 按设计返回 None,旧版却把它渲染成「?送 + 营业时间未知」——
用户既不知道为什么没店,流程还会在下一步拿 None 崩掉。现在 S3Z 如实报
每家开门时间,并给「约开门后送 / 换地址 / 先不送了」三条出路。

另:`--at` 模拟时刻骗不了服务端 —— 营业状态按**服务端真实时钟**返回,
凌晨用 `--at 12:00` 测营业分支仍会走打烊分支(离网测试不受影响,FakeApi 自己算)。

### 11. 照旧匹配不到是常态,不是异常(2026-10-11 实测)

盛源生活广场外送菜单 111 项**拉取完全正常**,却没有任何「安格斯」项 ——
铁律 3(菜单逐店逐渠道)的必然结果就是 `_usual()` 返回 None,这不是数据故障。
当次事故:`ask_items()` 没判空直接 `.get()`,对话当场崩溃;同一会话还发现
S5 分派里 `cands[i]` 越界会回落 `cands[0]`,选「看菜单」等于把照旧直接下单。
三条守门,缺一不可:

1. **`ask_items()` 必须判空**:如实说「常点的这套,这家店没有」,给一个替代
   (有替代给替代,没替代建议换店)。不许崩,不许装作照旧存在。`test_flow` I18 守门。
2. **非下单/导航选项必须在 cands 回落之前分派**:S5 分派要先认出「看菜单」(现进
   S5M/S5MP 分类翻页)与「换店」(回 S3B) —— `cands[i]` 越界回落 `cands[0]` 是
   **误下单级 bug**,点菜单却出订单是本域最严重的分派错误。`test_flow` I19 守门。
3. **测试盲区自省**:FakeApi 假菜单刻意包含照旧(见 `test_flow.py` FAKE_MENU 注释),
   意味着「照旧缺失」分支此前**零覆盖** —— 出事当天 29 项不变量全绿,两个 bug 照样逃逸。
   **新增任何降级/拦截路径,必须同步 test_flow 回归用例**,「全绿」才有资格当证据。

附带教训(同会话):`flow.py` 的 `__main__` 里 `turn_text()` 返回的是拼接文本(str)
而非 Turn,`print(t.text)` 不带 `--reply` 必崩 —— 修法是首轮从 `ctx._last_text /
_last_speech` 取话术。离网测试不覆盖 `__main__`(它绑定真实 API),改完必须手动空跑一次。

## 十、语音交互（**主入口**，不是可选）

**先说边界:麦当劳 MCP 的 35 个工具中零个语音接口**,描述里也零提及 ASR/TTS。
语音输入输出通道在宿主 App,不在 MCP 协议内。本模块负责的是
「把 flow 的每一轮变成能念出口的话」+「把用户说回来的话映射回选项」。

**架构(2026-10-11 阶段 A B 组已合并)**:
`voice.py` 曾自带一套 S1–S6 静态话术,与 `flow.py` 是两套状态机 —— 已删除。
现在每轮话术由 `flow.Turn` 同源产出:

| 字段 | 约束 | 验证 |
|---|---|---|
| `Turn.text` | ≤13 行、每行 ≤16 汉字（见第四节） | test_flow I7 |
| `Turn.speech` | 整轮 ≤60 字、单句 ≤30 字(约 6 秒),只念选项名**不念编号**,金额念中文(`cn_number`) | test_flow D1a–D1d |

**语音输入(B3)**:ASR 文本进 `_reply` 前先过 `voice.normalize_terms`
(打包→外带 / 车上取→得来速 / 不要芝士→去芝士);与选项名互相包含但没直接命中时,
走**复述确认**「您是说X吗?」→「对/是/嗯/回1」确认,「不是/回2」否认 —— 不瞎猜。

```bash
python3 scripts/voice.py --selfcheck    # 9 项自检(工具 + flow 口播不变量)
python3 scripts/voice.py --flow-demo     # 走完 S0→S8,每轮打印 text 与 speech(离网)
```

四条硬约束:

1. **不念编号**,只念选项名
2. **单句 ≤6 秒**(约 25–30 字)
3. **禁念内部信息**:`code` / `key` / 字段名 / 括号内部值 / `[依据]` / `[间隔]`
4. **识别错误必须显式复述**:"您是说麦香鱼吗?"不能默认听对了

术语等效词典:车上取/开车窗口/路边取 → 得来速;不要芝士/不加芝士 → 去芝士;冰少 → 少冰;随便/老样子 → 照旧。
